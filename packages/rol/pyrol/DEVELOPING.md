# Developing PyROL

PyROL's bindings are C++ code generated by
[Binder](https://github.com/RosettaCommons/binder) from ROL's and Teuchos'
headers, compiled with [pybind11](https://github.com/pybind/pybind11), plus a
thin pure-Python layer.

## Layout

```
pyrol/
├── CMakeLists.txt    builds the module; with PYROL_ENABLE_BINDER=ON it first runs Binder
├── pyproject.toml    pip packaging (scikit-build-core); CI copies it to the Trilinos root
├── python/           the pure-Python package, installed as pyrol/
│   ├── __init__.py       exports the commonly used classes; the rest go to pyrol.unsupported
│   ├── getTypeName.py    adapts the generated classes (keeps Python objects alive while C++
│   │                     uses them, SimOpt value() dispatch) and looks classes up by name
│   └── vectors/          NumPyVector
├── src/              hand-written C++
│   ├── Binder_Input.hpp, PyROL_ETI.hpp, PyROL_Teuchos_ETI.hpp, PyROL_stream.hpp
│   │                     Binder's input: the explicit instantiations decide which ROL
│   │                     templates are wrapped, and for which scalar type
│   ├── PyROL_Teuchos_Custom.hpp/.cpp
│   │                     dictionary-style access to Teuchos::ParameterList
│   ├── PyROL_clone.hpp, PyROL_clone_shared.hpp
│   │                     Vector::clone() for Python vectors (Teuchos::RCP / std::shared_ptr)
│   ├── PyROL_vector.hpp  binds every std::vector type as a Python sequence that lists,
│   │                     tuples and NumPy arrays convert to
│   └── CMakeLists.txt    compiles these together with the generated sources
├── scripts/          build-time tools; nothing here is installed
│   ├── PyROL_common.cfg  Binder configuration (what to wrap or skip, customizations)
│   ├── PyROL_RCP.cfg, PyROL_shared_ptr.cfg
│   │                     the settings for each ROL_Ptr, appended to the common file
│   ├── gather_includes.py
│   │                     prepares Binder's input
│   └── build_sdist.sh    builds an sdist, locally and in CI
├── test/             unittest suites, registered with CTest
│   ├── algorithm/        ROL's algorithms on small test problems
│   ├── bindings/         the bindings and the Python layer
│   └── examples/         runs the examples
└── example/
```

The generated sources (`binder/`) are not in the repository. They exist only
in a build directory and in the sdist published to PyPI, so building wheels
does not need Binder.

## How releases are built

The `Build Python interface` workflow (`.github/workflows/python.yml`, run
manually) has three jobs:

1. `build-sdist` builds Binder against LLVM 15, clones the latest Trilinos
   `develop`, copies this repository into `packages/rol`, and configures
   Trilinos with `PYROL_ENABLE_BINDER=ON`, which runs Binder. CPack then
   packages ROL, Teuchos and the generated sources, and `python -m build
   --sdist` turns that into the sdist.
2. `build-wheels` builds and tests the wheels from the sdist with
   cibuildwheel.
3. `publish-pypi` uploads everything, but only if the "publish" box was
   checked when the workflow was started.

A wheel holds only what PyROL needs at run time: the Python files, the
module and the shared libraries of ROL and Teuchos, without headers or
CMake package files (see the comments in `pyproject.toml`).

The `Test Python interface` workflow (`.github/workflows/pyrol.yml`) runs on
pull requests that change `pyrol/`. It builds PyROL from source for both
`ROL_Ptr=Teuchos::RCP` (used for the wheels) and `ROL_Ptr=std::shared_ptr`,
and runs all Python tests with CTest.

Versions pinned on purpose, to bump deliberately: pybind11 (in
`pyproject.toml`, `python.yml` and `pyrol.yml`), the Binder commit (in both
workflows) and cibuildwheel. Trilinos is always the latest `develop`. A new
pybind11 version can change pybind11's internal ABI (2.x and 3.x differ), and
then compiled extensions built with the old one cannot exchange objects with
PyROL.

## Building and testing from source

Configure Trilinos with this repository as `packages/rol`, for example:

```
cmake -G Ninja -B build -S <Trilinos> \
  -D BUILD_SHARED_LIBS=ON -D Trilinos_ENABLE_ROL=ON \
  -D ROL_ENABLE_PYROL=ON -D PYROL_ENABLE_BINDER=ON -D ROL_ENABLE_TESTS=ON \
  -D Python3_EXECUTABLE=<python with pybind11 and numpy>
cmake --build build --target pyrol
ctest --test-dir build -R ROL_PYTHON
```

Add `-D ROL_Ptr=std::shared_ptr` for the other pointer type. Without
`PYROL_ENABLE_BINDER`, the build expects previously generated sources in
`pyrol/binder`. `scripts/build_sdist.sh`, which CI also runs, builds an sdist
from a checkout; `pip wheel <sdist>` then builds a wheel from it.

## Binder

Build Binder against LLVM 15 or 16. With LLVM 18, Binder adds includes of
`*_Def.hpp` headers to the generated files, and they do not compile.

- **Linux:** install `clang-15 llvm-15 libclang-15-dev llvm-15-dev` (Ubuntu),
  and build Binder with
  `-D LLVM_DIR=/usr/lib/llvm-15/lib/cmake/llvm -D Clang_DIR=/usr/lib/llvm-15/lib/cmake/clang`.
- **macOS:** `brew install llvm@16`, then build Binder with
  ```
  cmake -G Ninja -S binder -B binder-build \
    -D LLVM_DIR=$(brew --prefix llvm@16)/lib/cmake/llvm \
    -D Clang_DIR=$(brew --prefix llvm@16)/lib/cmake/clang \
    -D BINDER_ENABLE_TEST=OFF \
    "-D CMAKE_EXE_LINKER_FLAGS=-L$(brew --prefix llvm@16)/lib -lLLVM"
  ```
  The linker flags are needed because Binder's CMake does not link
  `libLLVM` on macOS. When configuring Trilinos, also pass
  `-D "PyROL_BINDER_FLAGS=-isysroot;$(xcrun --show-sdk-path);-resource-dir;$(brew --prefix llvm@16)/lib/clang/16"`.
  `scripts/build_sdist.sh` does this for you.

## Exposing more of ROL

- To wrap another class template, add an explicit instantiation to
  `src/PyROL_ETI.hpp`.
- New classes appear in `pyrol.unsupported`, with the `_double_t` suffix
  removed. To export one from `pyrol` itself, add its name to
  `supported_objects` in `python/__init__.py`.
- To skip or customize something, edit `scripts/PyROL_common.cfg`, or the
  file for one pointer type if it only applies there.

## Known limitations

- Calling `dual()` from Python on a vector implemented in C++, such as
  `Vector_SimOpt`, fails ("return_value_policy = copy, but type is
  non-copyable"). C++ calls, and Python vectors, are not affected.
- Python overrides of `dual()` and `basis()` keep only their last result
  alive, like ROL's C++ vectors. The clone bridge covers Python subclasses of
  `Vector`, not of other C++ vector classes.
- On free-threaded Python the GIL is turned back on at import.
